# NovelMatch V1.0 技术开发说明书

**项目名称：** NovelMatch
**产品类型：** Windows 桌面端 AI 小说质量分析与筛选工具
**文档版本：** V1.0
**开发方式：** OpenCode + Vibe Coding
**产品原型：** 墨刀
**技术路线：** Tauri 2 + React + TypeScript + SQLite + 在线大模型 API

# 一、项目概述

## 1.1 产品定位

NovelMatch 是一款基于 AI 的个性化小说质量分析与筛选工具。

用户通过导入自己喜欢和讨厌的小说，建立个人阅读品味画像。之后输入一本待评估小说的链接，系统分析小说前十章的内容特征，并结合用户当前画像，生成个人阅读匹配度。

产品的核心价值不是判断一本小说是否符合大众审美，而是判断它是否符合当前用户的阅读偏好。

## 1.2 核心业务流程

整个产品围绕两个主要流程展开：

**流程 A：建立阅读品味画像**

1. 用户创建一套画像。
2. 设置画像名称和小说题材。
3. 导入喜欢的小说。
4. 对每本喜欢的小说进行七维度评分。
5. 导入讨厌的小说。
6. 对每本讨厌的小说选择第一差和第二差的维度。
7. 用户确认参考小说。
8. AI 分析参考小说，归纳用户的阅读偏好。
9. 生成并保存品味画像。
10. 用户可以查看和手动修改画像总结。

**流程 B：评估待选小说**

1. 用户选择已有画像。
2. 输入待评估小说链接。
3. 点击评估。
4. 系统获取小说前十章正文。
5. AI 分析小说的七个维度。
6. 系统将小说特征与当前用户画像进行匹配。
7. 生成匹配度百分比。
8. 保存评估记录。
9. 在右侧主区域展示评估报告。

## 2.3 架构原则

1. 不建设统一的云端 AI 网关。
2. 不建设中心化用户数据库。
3. 用户数据默认保存在本地电脑。
4. 模型调用直接从桌面端发起。
5. AI 业务逻辑与具体模型服务商解耦。
6. 前端不得直接持有 API Key。
7. 所有本地数据库操作通过 Tauri Commands 进行。
8. AI 返回的数据必须经过结构化解析和校验后才能进入业务流程。

**重要说明：**

用户自行配置 API Key 后，模型调用费用由用户承担。

API Key 存储在 Windows 安全凭据管理器中，前端不应直接读取密钥。模型请求应由 Rust 后端发起，避免在 WebView、前端状态或日志中暴露密钥。

本地安全存储可以降低密钥泄露风险，但不能保证密钥在用户拥有本机控制权的情况下绝对不可提取。

# 三、前端页面与交互设计

## 3.1 页面整体布局

采用左侧固定导航栏 + 右侧主工作区。

左侧导航栏：

- NovelMatch Logo。
- 用户画像列表。
- 新建画像入口。
- 模型配置入口。

右侧主工作区根据用户当前操作切换内容。

画像列表纵向排列，点击不同画像切换当前工作台。

## 3.2 页面清单

| 页面         | 功能                             |
| ------------ | -------------------------------- |
| 初始空状态   | 尚未创建画像时展示               |
| 画像工作台   | 展示当前画像和小说评估入口       |
| 新建画像     | 创建画像名称和选择题材           |
| 喜欢小说导入 | 导入正向参考小说并打分           |
| 讨厌小说导入 | 导入负向参考小说并选择缺点       |
| 参考小说确认 | 确认本次画像生成使用的小说       |
| 画像生成进度 | 展示 AI 生成状态                 |
| 画像编辑     | 修改 AI 生成的画像总结           |
| 模型配置     | 配置 API Key、模型名称、API 地址 |
| 小说评估进度 | 展示当前小说评估状态             |
| 评估报告     | 展示小说匹配度百分比             |

页面的具体布局、按钮名称、弹窗和交互行为以现有墨刀原型为准。开发时先检查原型中的完整页面和交互，不自行重新设计产品流程。

## 3.3 画像创建

用户创建画像时需要填写：

- 画像名称。
- 小说题材。

预设题材：

- 玄幻
- 仙侠
- 都市
- 历史
- 科幻
- 悬疑
- 言情
- 武侠
- 游戏竞技
- 其他（自定义）

约束：

1. 每套画像只关联一个题材。
2. 同一题材允许创建多套画像。
3. 画像名称由用户自定义。
4. 不同画像之间的数据相互独立。
5. 用户可以创建、编辑、切换和删除画像。

## 3.4 喜欢的小说导入

每本喜欢的小说需要记录：

- 小说名称。
- 小说来源或链接（如有）。
- 用户对七个维度的评分。

七个维度：

1. 文笔
2. 剧情
3. 人物塑造
4. 世界观
5. 节奏
6. 创意
7. 爽点

每个维度采用 1–5 星评分。

评分解释：

- 1 星：非常不满意。
- 2 星：不满意。
- 3 星：一般。
- 4 星：满意。
- 5 星：非常满意。

评分由用户主观决定，不使用大众评分替代。

## 3.5 讨厌的小说导入

每本讨厌的小说只需要回答两个问题：

- 这本书最差的方面是什么？
- 这本书第二差的方面是什么？

可选维度与喜欢小说保持一致：

文笔、剧情、人物塑造、世界观、节奏、创意、爽点。

约束：

1. 两次选择不能重复。
2. 第二差维度从剩余选项中选择。
3. 不要求用户逐项打分。
4. 用户可以只导入喜欢的小说，也可以只导入讨厌的小说。

至少存在一本参考小说才允许生成画像。如果喜欢和讨厌两类都没有小说，则不能生成画像。

## 3.6 画像展示

生成画像后展示：

- 画像名称。
- 画像题材。
- AI 生成的整体品味总结。
- 偏好关键词。
- 喜欢的特征。
- 不喜欢的特征。
- 编辑入口。
- 小说评估入口。

前台不展示复杂雷达图或冗长的七维度分析报告。

用户可以编辑整体画像总结，修改后的内容应保存到本地数据库。

## 3.7 模型配置页面

严格遵循现有墨刀原型，只保留三个输入框：

| 输入框   | 字段       | 示例                                                  |
| -------- | ---------- | ----------------------------------------------------- |
| API Key  | api_key    | 用户自行填写                                          |
| 模型名称 | model_name | deepseek-chat                                         |
| API 地址 | base_url   | [https://api.deepseek.com](https://api.deepseek.com/) |

不增加服务商下拉框，不增加 Temperature、Top P 等高级参数。

功能：

1. 填写三个字段。
2. 保存配置。
3. 修改已有配置。
4. 清空或删除配置。
5. 验证配置是否可用。

预设服务商通过使用说明提供示例，不通过额外的服务商选择控件实现。

API 地址统一定义为 Base URL。程序根据统一接口规范拼接 `/chat/completions` 等路径，避免重复拼接。

# 四、本地数据库设计

## 4.1 数据存储原则

使用 SQLite 保存用户业务数据。

数据库文件保存在 Windows 用户数据目录，不得放在程序安装目录。

建议目录：

```
%APPDATA%/NovelMatch/
│
├── novelmatch.db
├── logs/
└── backups/
```

API Key 不写入 SQLite，单独存放于 Windows Credential Manager。

```

  │
  ├── reference_books
  │       │
  │       ├── user_ratings
  │       │
  │       └── book_analyses
  │
```

删除画像时，应在事务中处理关联数据，避免产生孤立记录。删除前需要用户确认。

## 4.4 数据持久化要求

- 关闭程序后数据不丢失。
- 重启程序后恢复上次画像列表。
- 修改画像后及时保存。
- 重要写操作使用 SQLite 事务。
- 数据库结构通过 Migration 管理。
- 支持本地数据备份和恢复。
- 卸载软件时明确提示本地数据是否保留。

# 五、模型配置与 AI 调用模块

## 5.1 模型调用原则

V1.0 采用 OpenAI Chat Completions 兼容接口。

用户输入：

- API Key
- 模型名称
- API Base URL

系统通过统一模型适配层发起请求。

不在业务模块中直接编写 DeepSeek、OpenAI 等特定服务商的调用逻辑。

## 5.2 模型配置数据

建议本地配置对象：

```
{
  "model_name": "deepseek-chat",
  "base_url": "https://api.deepseek.com"
}
```

API Key 单独保存到 Windows Credential Manager。

密钥通过 Tauri 后端读取，并且只在实际请求时使用。

## 5.3 统一模型接口

建议抽象以下函数：

```
interface ModelConfig {
  modelName: string;
  baseUrl: string;
}

interface ModelMessage {
  role: "system" | "user" | "assistant";
  content: string;
}

interface ModelResponse {
  content: string;
  model: string;
  usage?: {
    promptTokens?: number;
    completionTokens?: number;
  };
}

interface AIService {
  testConnection(): Promise<boolean>;

  chat(
    messages: ModelMessage[]
  ): Promise<ModelResponse>;
}
```

上述接口为前端与 Rust 服务层的逻辑约定，实际模型请求由 Rust 后端实现。

## 5.4 模型连接测试

测试连接时：

1. 检查三个输入框是否填写。
2. 检查 API 地址格式。
3. 检查 API Key 是否存在。
4. 发起轻量级模型请求。
5. 检查模型是否正常返回。
6. 向前端返回连接结果。

需要区分：

- 配置缺失。
- API Key 无效。
- API 地址错误。
- 模型名称不存在。
- 请求超时。
- 服务商限流。
- 模型服务异常。
- 返回内容格式错误。

不得将所有异常统一显示为“连接失败”。

## 5.5 AI 请求管理

建议统一实现：

- 请求超时。
- 错误分类。
- 有限次数重试。
- 网络异常提示。
- 请求取消。
- 结构化 JSON 响应解析。
- 日志脱敏。

只对超时、临时网络错误、限流等可恢复错误进行有限重试。对于 API Key 无效、模型不存在等错误，不应反复重试。

# 六、AI 核心业务模块

NovelMatch 的核心 AI 能力分为三个阶段：

1. 参考小说内容分析。
2. 用户阅读品味画像生成。
3. 待评估小说与用户画像匹配。

## 6.1 七维度小说分析

AI 需要从小说文本中提取以下七个维度的特征。

| 维度     | 分析内容                                   |
| -------- | ------------------------------------------ |
| 文笔     | 语言表达、描写能力、行文流畅度、叙述风格   |
| 剧情     | 情节设计、逻辑连贯性、冲突安排、故事推进   |
| 人物塑造 | 人物性格、人物动机、人物成长、人物关系     |
| 世界观   | 世界设定、规则体系、背景完整性、设定一致性 |
| 节奏     | 信息密度、情节推进速度、铺垫与高潮安排     |
| 创意     | 题材新颖性、设定独特性、情节创新           |
| 爽点     | 情绪反馈、期待兑现、成长反馈、冲突释放等   |

爽点不使用固定的预设分类。

AI 应结合参考小说内容，自动归纳用户喜欢或排斥的爽点类型。

## 6.2 小说分析输出结构

建议 AI 返回统一 JSON：

```
{
  "title": "小说名称",
  "dimensions": {
    "writing": {
      "features": [],
      "description": ""
    },
    "plot": {
      "features": [],
      "description": ""
    },
    "character": {
      "features": [],
      "description": ""
    },
    "worldbuilding": {
      "features": [],
      "description": ""
    },
    "pacing": {
      "features": [],
      "description": ""
    },
    "creativity": {
      "features": [],
      "description": ""
    },
    "payoff": {
      "features": [],
      "description": ""
    }
  }
}
```

这里的 features 用于保存可比较的文本特征，description 用于保存自然语言总结。

AI 不应只输出“文笔好”“剧情差”等简单判断，而应尽量提取具体特征。

例如：

```
{
  "writing": {
    "features": [
      "语言简洁",
      "描写自然",
      "对话流畅",
      "叙述节奏稳定"
    ],
    "description": "整体语言表达较为流畅，描写克制，阅读负担较低。"
  }
}
```

上述内容仅为结构示例，不代表预设小说评分。

## 6.3 品味画像生成

画像生成需要综合三类信息：

1. 用户喜欢的小说。
2. 用户讨厌的小说。
3. 用户对小说七个维度的主观反馈。

处理流程：

```
参考小说
   │
   ▼
AI 分析七个维度
   │
   ▼
提取文本特征
   │
   ▼
关联用户主观评价
   │
   ▼
归纳正向偏好
   │
   ▼
归纳负向偏好
   │
   ▼
提炼爽点偏好
   │
   ▼
生成用户阅读品味画像
   │
   ▼
保存至 SQLite
```

具体要求：

- 喜欢的小说用于学习用户认可的内容特征。
- 讨厌的小说用于学习用户排斥的内容特征。
- 七维度评分用于区分用户重视的方面。
- 第一差和第二差用于识别用户最敏感的负面因素。
- AI 应提取多本小说之间反复出现的共同特征。
- 不应将单本小说的偶然特征直接视为用户稳定偏好。
- 正向和负向样本可以单独存在。
- 只有一种类型的参考样本时，画像应明确反映证据范围，不能虚构另一类偏好。

画像生成结果建议分为：

```
{
  "summary": "整体阅读品味总结",
  "keywords": [],
  "positive_preferences": [],
  "negative_preferences": [],
  "dimension_preferences": {
    "writing": "",
    "plot": "",
    "character": "",
    "worldbuilding": "",
    "pacing": "",
    "creativity": "",
    "payoff": ""
  }
}
```

其中：

- summary：前台展示的整体画像总结。
- keywords：偏好关键词。
- positive_preferences：喜欢的内容特征。
- negative_preferences：不喜欢的内容特征。
- dimension_preferences：七维度的偏好描述，供后续匹配使用。

## 6.4 小说匹配度计算

这是 NovelMatch 最重要的业务环节。

不能简单地将七维度小说分析结果求平均，也不能只根据小说自身质量打分。

匹配度必须回答：

**这本小说的内容特征，与当前用户的阅读品味有多接近？**

建议采用“AI 特征匹配 + 加权汇总”的方法。

第一步：分析待评估小说，获得七维度内容特征。

第二步：读取当前画像中的七维度偏好描述、正向特征和负向特征。

第三步：AI 对每个维度进行匹配评估，得到维度匹配分数。

第四步：根据用户偏好强度计算综合匹配度。

计算形式：

[
S=\frac{\sum_{i=1}^{7}w_i s_i}{\sum_{i=1}^{7}w_i}\times100
]

其中：

- (S)：最终匹配度。
- (w_i)：第 (i) 个维度的偏好权重。
- (s_i)：该维度的匹配得分，范围为 0–1。

权重应结合用户的评分和负向排序，以及画像生成结果确定。

V1.0 可以先使用 AI 生成的结构化偏好权重和维度匹配得分。具体权重生成规则需要通过真实样本测试和调整，不应直接把七个维度默认视为同等重要。

特别注意：

- 负向偏好应产生惩罚作用。
- 用户高度重视的维度应具有更高权重。
- 用户明确排斥的特征应重点考虑。
- 不应将 AI 对小说的绝对质量评价直接当作个人匹配度。
- 对正文获取不完整、分析证据不足的情况，应提示结果可靠性受限。

匹配度的具体计算方式需要通过后续真实用户反馈验证。V1.0 的百分比是模型驱动的匹配估计，不应宣传为经过统计验证的客观概率。

## 6.5 评估报告

前台报告保持极简。

展示：

- 小说名称。
- 匹配度百分比。
- 当前使用的画像。
- 评估章节范围。

不展示：

- 七维度详细评分。
- 复杂雷达图。
- 长篇分析报告。
- 冗长匹配依据。
- 阅读建议。

用户的核心诉求是快速得到是否值得尝试阅读的判断。

# 七、小说正文获取模块

## 7.1 功能目标

用户输入小说链接，系统获取小说正文并提取前十章内容。

正文获取和 AI 分析是两个独立模块，不能将 URL 直接交给模型并假设模型一定能够访问。

## 7.2 处理流程

```
用户输入小说链接
       │
       ▼
URL 合法性检查
       │
       ▼
访问页面
       │
       ▼
获取页面内容
       │
       ▼
提取小说正文
       │
       ▼
识别章节结构
       │
       ▼
提取前十章
       │
       ▼
正文完整性检查
       │
       ▼
交给 AI 分析
```

## 7.3 正文获取要求

- 支持合法公开访问的小说页面。
- 识别小说标题。
- 识别章节名称。
- 提取章节正文。
- 按顺序组织章节。
- 尽可能保证前十章完整。
- 无法获取时明确反馈原因。
- 不允许将网页广告、评论区、目录等误识别为正文。

## 7.4 站点兼容策略

不同小说平台的网页结构不同。

建议使用站点适配器设计：

```
interface BookSourceAdapter {
  canHandle(url: string): boolean;

  getBookInfo(url: string): Promise<BookInfo>;

  getChapters(url: string): Promise<Chapter[]>;

  getChapterContent(
    chapterUrl: string
  ): Promise<string>;
}
```

初期只实现已经验证可用的小说来源。

不要在 V1.0 中承诺支持所有网络小说平台。

## 7.5 内容处理限制

必须遵守网站访问规则和版权要求。

- 不绕过登录、付费墙和访问控制。
- 不绕过平台反爬机制。
- 不进行未经授权的批量抓取。
- 不向其他用户分发未经授权的小说正文。
- 正文默认只用于当前分析任务，不长期保存完整原文。
- 用户应明确知晓正文可能被发送到其配置的第三方模型服务。

考虑到模型上下文长度，应先计算正文长度，必要时分章节分析，再汇总结果。

# 八、任务管理与异常处理

## 8.1 画像生成任务

画像生成属于耗时操作，需要任务状态管理。

建议状态：

- pending：等待处理。
- fetching：获取参考小说内容。
- analyzing：AI 分析参考小说。
- generating：生成画像。
- completed：完成。
- failed：失败。

前端展示进度和当前步骤。

不能只显示一个无限旋转的加载动画。

## 8.2 小说评估任务

建议状态：

- pending
- fetching
- extracting
- analyzing
- matching
- completed
- failed

用户点击评估后：

1. 创建评估任务。
2. 展示进度弹窗。
3. 执行正文获取。
4. 执行七维度分析。
5. 执行画像匹配。
6. 保存结果。
7. 进入右侧评估报告页面。

任务失败时，应保留明确错误信息，允许用户重新尝试。

## 8.3 异常处理

| 异常            | 处理方式                 |
| --------------- | ------------------------ |
| 未配置模型      | 提示先配置模型           |
| API Key 无效    | 提示检查 API Key         |
| 模型不存在      | 提示检查模型名称         |
| API 地址错误    | 提示检查 API 地址        |
| 网络中断        | 提示检查网络并允许重试   |
| 模型请求超时    | 允许有限次数重试         |
| 模型返回非 JSON | 尝试修复或重新请求       |
| 小说链接无效    | 提示检查链接             |
| 页面无法访问    | 提示当前来源暂不支持     |
| 正文提取失败    | 提示无法获取小说内容     |
| 正文不足十章    | 按实际可获取章节提示用户 |
| AI 分析失败     | 保存错误状态并允许重试   |
| 数据库写入失败  | 回滚事务并提示用户       |

# 十一、非功能性要求

## 11.1 性能

- 软件启动过程应尽量快速。
- 本地画像和历史记录应即时加载。
- 长时间 AI 请求不得阻塞界面。
- 耗时任务使用异步方式执行。
- 正文较长时采用分章节处理。
- 避免将完整小说正文长期加载到前端状态中。

## 11.2 安全

- API Key 不写入前端代码。
- API Key 不写入普通日志。
- API Key 使用 Windows 安全凭据存储。
- 网络请求使用 HTTPS。
- 限制小说 URL 的协议和目标地址，防止访问本机服务、内网和其他非预期地址。
- 不执行从网页提取的脚本。
- 数据库文件保存在用户数据目录。
- 不默认上传用户画像和阅读记录。

## 11.3 隐私

需要向用户说明：

1. 用户画像和评分默认保存在本地。
2. 小说正文会发送到用户配置的模型服务进行分析。
3. 第三方模型服务商可能按照自身隐私政策处理请求数据。
4. 用户自行承担模型调用费用。
5. 用户可以删除本地画像和评估记录。
6. 软件不建立中心化用户数据库。

## 11.4 可维护性

- 前后端分层。
- AI 服务统一封装。
- 数据库使用 Migration。
- Prompt 单独管理并版本化。
- 错误处理统一。
- 核心业务逻辑避免依赖具体 UI 组件。
- 为匹配度计算和正文提取模块编写测试。

- Rust 使用明确的错误类型。
- 数据库操作使用参数化查询。
- AI 返回值进行 Schema 校验。
- 关键业务模块编写单元测试。
- 不在代码中硬编码 API Key。
- 不在提交记录和调试日志中暴露用户密钥。

# 十三、V1.0 最终验收标准

NovelMatch V1.0 必须完整跑通以下场景：

**场景一：新用户建立画像**

1. 用户安装并打开软件。
2. 创建一套仙侠小说画像。
3. 导入喜欢的小说。
4. 对喜欢的小说进行七维度评分。
5. 导入讨厌的小说。
6. 选择每本讨厌小说的第一差和第二差维度。
7. 配置 API Key、模型名称和 API 地址。
8. 点击生成画像。
9. AI 分析参考小说。
10. 系统生成阅读品味总结。
11. 用户可以编辑并保存画像。

**场景二：用户评估新小说**

1. 用户打开已有画像。
2. 输入一本待评估小说的链接。
3. 点击评估。
4. 系统获取前十章正文。
5. AI 分析小说七个维度。
6. 系统结合用户画像计算匹配度。
7. 生成匹配度百分比。
8. 右侧主区域打开评估报告。
9. 用户可以返回画像工作台。
10. 评估记录保存到本地。

**场景三：多画像管理**

1. 用户创建多套不同题材或不同风格的画像。
2. 各画像独立保存参考小说和评价。
3. 用户可以切换画像。
4. 用户使用不同画像评估同一本小说。
5. 每次评估记录正确关联对应画像。

**最终交付物：**

- Windows 安装包。
- 完整项目源代码。
- SQLite 数据库及 Migration。
- 模型配置与调用模块。
- AI Prompt 文件。
- 技术文档。
- 测试记录。
- 用户使用说明。

# 十四、开发优先级总结

| 优先级 | 模块           | 交付目标               |
| ------ | -------------- | ---------------------- |
| P0     | 桌面框架       | 软件可以运行           |
| P0     | 原型还原       | 页面与交互完成         |
| P0     | SQLite         | 数据能够持久化         |
| P0     | 模型配置       | 三个输入框可正常使用   |
| P0     | AI 接入        | 可以调用用户配置的模型 |
| P0     | 品味画像       | 可以真正生成画像       |
| P0     | 小说评估       | 可以生成匹配度报告     |
| P1     | 历史记录       | 可以查看过往评估       |
| P1     | 数据备份       | 支持备份和恢复         |
| P1     | 异常恢复       | 网络和模型异常可恢复   |
| P2     | 多模型任务分配 | 暂不开发               |
| P2     | 主动小说推荐   | 暂不开发               |
| P2     | 云端同步       | 暂不开发               |

**最终开发原则：先做出一个完整、稳定、可以真实使用的桌面端 MVP，再考虑扩展功能。**

不要为了技术复杂度牺牲产品闭环。NovelMatch 的核心竞争力是能否从用户真实的阅读偏好中提取有价值的特征，并据此给出可信的个性化匹配结果。
